# Build Roadmap: Cross-Platform Agent for Windows and Linux

> Execution order and release priorities are defined in [BUILD_PLAN.md](BUILD_PLAN.md). Use that plan to decide what to do next; this roadmap remains the detailed feature inventory.

- **Modern MCP control-flow response safety — 2026-10-27:** stdio and Streamable HTTP now inspect 2026-07-28 `resultType` responses. `complete` and the specification's absent-as-complete form pass through; `input_required` and task results fail with explicit unsupported-feature errors, while unknown types fail as invalid responses. Focused regressions pass on both transports. This closes the unsafe interpretation gap for those control-flow results; full capability, content-block, and method-result schema validation remains open.
- **Interrupted tool-call resume safety — 2026-10-27:** when a saved transcript contains proposed tool calls without persisted results, resume now appends untrusted error observations stating that each missing outcome is unknown. Existing results remain intact, recovery is idempotent, and actions are never re-executed as part of transcript repair. Focused recovery and AgentRuntime resume regressions pass. Broader crash injection at every tool/audit/session persistence boundary remains open.
- **Committed session-write recovery — 2026-10-27:** if an atomic session rename succeeds but the containing-directory flush fails, the session store now advances the in-memory revision and reports a filesystem warning while treating the visible record as committed. This keeps active runtime state aligned and allows safe retry. A Linux-only fault-injection regression checks the committed record and subsequent save; hosted Linux verification is pending.

## Purpose and scope

This document turns the supplied product roadmap into an ordered, ticket-ready implementation plan. The product supports Windows and Linux only. It has one shared agent core used by the CLI, desktop app, and VS Code extension; local OpenAI-compatible model servers and remote providers; routing; retrieval and project memory; sandboxing and approvals; persistent sessions; extension support; observability; evaluation; and release packaging.

The plan is dependency ordered. Each work item should be tracked as an issue with an owner, acceptance criteria, and links to its tests and documentation. The phase durations are estimates for a small experienced team, not a promise. Several phases can overlap after their interfaces are stable. A single engineer should expect a longer schedule.

- `[x]` means the behavior and required evidence are complete on every platform the item claims to support.

## Product invariants

1. Windows and Linux are first-class platforms. Every shared feature has platform tests and CI coverage on both.
2. CLI, GUI, and IDE surfaces call the same agent runtime and use the same versioned session format.
3. No model response, retrieved file, web result, MCP result, or skill content can override system policy or grant tool permissions.
4. In assisted mode, tool permissions are enforced by the runtime and operating-system boundary, not merely by prompt instructions. Unrestricted mode is the default local automation profile and bypasses app policy; the operating system still applies the current account's permissions. Users can select Assisted mode explicitly.
5. Credentials are fetched only when a provider/tool call needs them. OS-vault values are never exposed as machine-wide files to the model, and provider credentials remain in the provider transport; unrestricted filesystem access may expose other credential files in the current OS account to tools and model context. Session persistence redacts recognizable credential patterns in a clone for every autonomy mode; legacy data and arbitrary secret encodings remain outside that guarantee.
6. Budget limits and cancellation are enforced in the runtime. A UI indicator alone is not enforcement.
7. Persistent memory and retrieval are project-scoped by default, inspectable, editable, and removable.
8. Every feature has a defined failure mode, user-visible status, and recovery path.

## Recommended initial architecture

- **Core and CLI:** The shared agent core, one-shot CLI, service, API, and browser UI use Node.js built-in modules, with platform-specific operations behind small adapters. The optional Ink/React terminal composer is dynamically loaded only for `--tui`, so the bundled desktop service remains independent of those packages.
- **Desktop app:** Tauri 2 hosts the existing shared UI and authenticated local API. The desktop build stages a pinned Node runtime; native workflows and production installer validation remain in Phase 7/8.
- **IDE:** VS Code extension as a client of the shared local API. Do not create a second agent loop in TypeScript.
- **Persistence:** SQLite for indexed/session metadata and transactional state; versioned JSON export for portability and debugging. Keep large content blobs separately addressable where needed.
- **Configuration:** TOML with explicit user and project layers, documented precedence, validation, and redaction.
- **Provider protocol:** Internal provider trait with normalized response/error types; OpenAI-compatible HTTP implementations first.
- **Tool protocol:** Versioned JSON Schema-compatible tool definitions plus runtime-enforced permission metadata.
- **Compatibility:** Declare supported Windows versions, Linux distributions/kernel capabilities, Rust/toolchain versions, and minimum terminal/UI requirements before Phase 0 closes.

These choices are starting defaults. Record changes as architecture decision records (ADRs) before dependent work expands.
