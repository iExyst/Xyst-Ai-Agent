# Local control API

`node src/cli.mjs serve [--port 0]` starts the shared agent runtime as a local service. It binds only to IPv4 loopback. Open the returned origin with `/app` to use the bundled browser UI. That static shell is available only to local top-level same-site navigation and embeds the ephemeral bearer token in memory for its same-origin API client; the versioned API routes themselves still require `Authorization: Bearer <token>`. Session summaries include an automatically generated title from the first user message, unless the user renames the session. A successful startup writes one JSON line to stdout:

```json
{"url":"http://127.0.0.1:49152","token":"<ephemeral bearer token>","api_version":1}
```

The token is generated from 256 random bits for each process and remains in memory. A desktop host should capture the service stdout pipe privately, keep the token in memory, and stop the process when the client closes. Do not write the bootstrap record to logs or persistent settings. The CLI service does not save the token to disk.

Every versioned `/v1` operation, including health checks and event streams, requires `Authorization: Bearer <token>` except the single-use, short-lived application-update download capability URL. CORS preflight only validates the configured origin and requested method. The service validates that the socket peer is loopback and the `Host` header names `127.0.0.1` or `localhost`. Same-origin requests from the bundled UI work without CORS configuration. Other browser clients must list their exact origin under `api.allowed_origins`; wildcard, credentials, paths, query strings, and fragments are rejected by config validation. Configure browser origins only for clients you control.

## Version 1 routes

Error responses use `{ "error": "...", "code": "OPTIONAL_CODE" }`. `error` is the human-readable message; `code` is an optional stable machine-readable identifier and may be absent on older or generic validation paths. Clients should handle unknown or absent codes using a generic API error.

When a user explicitly requests one uppercase token as the exact final answer, the runtime removes preceding prose only when the model also ends its response with that same token on a separate line. Other responses are preserved. For streaming runs with this explicit format, the final response is buffered until it can be normalized and then emitted as one assistant delta; if the user cancels mid-response, buffered partial text is emitted before shutdown.

Request bodies are JSON and limited to 1 MB, except runs with image attachments (24 MiB) and session import (50 MiB). Image files are limited to 10 MiB each and 16 MiB combined before preprocessing; large images are resized to at most 2048 pixels per edge and JPEG-compressed. Linux resizing requires ImageMagick; Windows resizing uses Windows PowerShell and System.Drawing. Images are sent to the selected vision-capable provider for the current run, while session records retain only MIME type, dimensions, byte count, and SHA-256 metadata. At most two runs may execute concurrently by default; `api.max_concurrent_runs` can be set from 1 to 16. Approval requests expire after five minutes by default; configure `api.approval_timeout_ms` from 1,000 to 300,000 ms.

Session grants are bound to a hash of the exact tool name and canonical argument object. They do not grant access to other paths or changed arguments, expire within 24 hours, are cleared when a session is forked, and can be revoked after the session run ends. Each session can hold at most 100 unexpired grants; grant records contain no raw arguments.

Workspace managed approval rules support `tool`, `path_glob`, and `command_glob` scopes with allow or deny decisions. Their duration must be 60 seconds to 30 days; expired rules remain visible until revoked. Deny rules are evaluated before allow rules, and configuration denials plus the sensitive-data boundary cannot be overridden. Rule creation and revocation are written to the workspace audit log. Revocation affects subsequent tool decisions; an action already approved and executing is not interrupted.

The API is a thin adapter: tool arguments, permissions, approvals, cancellation, model calls, budgets, and persistence remain enforced by the shared runtime and existing stores. Project and optional global memory remain user-maintained data; memory text is untrusted context and does not grant permissions. This local service is not a multi-user network service. Any client holding its token has the current user's agent permissions, subject to runtime approvals and policy.

Agent-launched background processes use `start_background_process` and require the normal run approval. Jobs run with direct argv, filtered environment, the current run workspace (including a selected managed worktree), and required Bubblewrap isolation when configured. Output is bounded and redacted before persistence. Process managers in other live processes show a job as `unmanaged` and refresh its record from disk; they cannot signal it. When the owner exits, the manager verifies a stored OS identity before allowing recovery: matching jobs become `recoverable`, absent jobs become `exited`, reused PIDs become `identity_mismatch`, and unverifiable identities remain `orphaned`. Only a verified `recoverable` job can be stopped; deleting active, unmanaged, or orphaned records is refused. Linux recovery requires Python 3.9+ and Linux 5.3+ pidfd support and rechecks identity while holding a pidfd before signaling the process group; it fails closed when pidfd is unavailable. If the group leader has already been reaped, remaining descendants cannot currently be identified and safely stopped. Windows verifies and terminates the root process through one open handle; Windows descendants are not currently reattached as a process tree. Identity capture depends on readable `/proc` data on Linux or Windows PowerShell process inspection, and fails closed when unavailable.

Session mutations return `409` when a run is active or a concurrent writer changed the session. Session file writes are serialized with per-session lock files and revision checks. Worktree runs and removals coordinate through cross-process leases under `.agent/worktree-locks`; a lease left by a crash fails closed. Verify its recorded PID and host before manually removing the stale lease file.

Runs can select a managed worktree by ID. New sessions are persisted with that worktree path, and later runs that resume the session automatically use the same still-registered worktree. Worktree paths supplied by clients are never accepted; the server resolves IDs against Git's registered worktrees.
