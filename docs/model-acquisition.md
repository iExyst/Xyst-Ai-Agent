# Model discovery and acquisition

Model discovery uses Hugging Face Hub's public API and an optional token stored with `hf auth set`. Search and repository inspection require `model discovery on`; online discovery is off by default. The CLI can inspect repository metadata and file sizes without downloading content.

```sh
xyst model discovery on
xyst hf search "Qwen coder GGUF"
xyst hf model Qwen/Qwen2.5-Coder-1.5B-Instruct-GGUF
xyst hf recommend "local coding assistant"
```

Downloads are opt-in separately with `model downloads on`. The download command resolves one GGUF artifact, rejects gated/private repositories, and enforces `models.maxDownloadBytes` (default 20 GiB). Before starting, Xyst checks free space on the LM Studio model directory and the operating system temporary volume, requiring the artifact size plus a 5% margin on both. It reads `LM_STUDIO_MODEL_DIR` when set, otherwise the LM Studio `downloadsFolder` from `~/.lmstudio/settings.json`, and falls back to the documented `~/.lmstudio/models` directory. The check uses the nearest existing parent when a configured directory has not been created yet. The preflight result and paths are saved with the job in SQLite. LM Studio does not document the downloader's staging strategy, so requiring room for a full temporary copy is conservative and may reject a download that would have streamed directly to the model directory.

Recommendations include free space and required size (artifact plus a 5% margin) for both the model-directory volume and the system temporary volume, plus a combined `diskSufficient` flag. The desktop disables a recommendation's download button when either volume lacks space; the CLI download command repeats both checks immediately before starting. These checks are conservative because the LM Studio downloader's staging strategy is undocumented.

```sh
xyst model downloads on
xyst hf download Qwen/Qwen2.5-Coder-1.5B-Instruct-GGUF Q4_K_M
xyst hf download-status <job-id>
xyst hf verify-download <job-id>
```

The job ID accepted by `hf download-status`, `hf verify-download`, and `hf downloads` is the Xyst download record ID or LM Studio job ID. On completion, Xyst checks LM Studio's local inventory and stores whether a matching model was found (or whether inventory could not be checked) in the download record. If an import was recorded as uncertain after a verified artifact was handed to LM Studio, `hf download-status` can reconcile it only when the saved artifact identity and SHA-256 are present and exactly one inventory model matches the repository; missing or ambiguous matches remain uncertain. `hf verify-download` sends a small generation probe and records the response. It reuses the target model's existing instance when available; if it would have to load a new instance while another model is active, it refuses to disturb that model. It unloads only an instance it started. The desktop transfer queue exposes the same verification action. Explicit `hf download` uses LM Studio's downloader and its configured Hub credentials; Xyst does not transfer those files itself or run repository code. For gated models, accept the model's license and configure Hub access in LM Studio first.

Agent auto-acquisition uses a separate pinned Hugging Face streaming path when no local LLM declares enough context for a task and discovery is enabled. Its generic capability search is capped at 20 Hub results and never includes the task objective or workspace content. With automatic downloads off, Xyst reports a recommendation and its declared context; with downloads on, it continues only for a compatible artifact set whose Hugging Face license tag exactly matches the saved `models.allowedLicenses` list. The list defaults to empty, so automatic acquisition stays blocked until the user records acceptable lowercase tags after reviewing the relevant model cards. License metadata that is missing or not on the list is never downloaded automatically. Context-constrained recommendations require a pinned model revision and a recognized context length from its config, a pinned `base_model` config referenced by its model card, or an explicit context statement in the pinned model card. Artifact SHA-256 can come from the Hub's `lfs.sha256` or 64-character `lfs.oid` field; Xyst still verifies every downloaded byte against that pinned digest. A public ungated repository, file sizes, and SHA-256 metadata for every selected file are also required. Xyst checks the aggregate download limit and free space on both the model volume and temporary volume. Each file gets up to three attempts; interrupted transfers retry from a validated HTTP byte range, and a server that ignores the range causes a safe restart from byte zero. Staging paths and artifact identities are saved in SQLite, so a later acquisition of the same pinned revision and file set reuses surviving partials; full files are hashed before reuse, and all bytes and SHA-256 values are checked before import. Interrupted transfers retain their valid partial bytes for recovery; corrupt or overlong partials are discarded. Xyst imports a single-file model through `lms import` with `--user-repo`, `--copy`, and `--yes`. Complete split GGUF sets are copied with exclusive creation into the LM Studio model directory under `<owner>/<repository>/`; a matching companion `mmproj` is included for image tasks. Incomplete shards, ambiguous projectors, unsafe filenames, and existing destination files are rejected. After installation, Xyst checks local inventory and declared context/modality, performs a small generation probe (and an image probe for vision acquisition), loads the verified model with the estimated task context when LM Studio reports sufficient capacity, records the selection reason and metadata source, and continues the task. A failure after bundle files have been installed is recorded as uncertain, with verified files left in place for LM Studio to inspect.

`hf recommend` searches at most twenty public Hugging Face matches and returns up to five repositories with a compatible GGUF artifact set each. It skips gated/private repositories, incomplete shard sets, and unrelated companion files; a vision-required recommendation includes one unambiguous matching `mmproj` projector. It checks the configured aggregate download cap and ranks artifact sets first by estimated concurrent RAM fit, estimated fit on the largest single NVIDIA GPU, free space on both download volumes, then quantization. Across repositories, those resource-fit results are followed by availability of structured Hub-listed evaluation evidence and finally Hub downloads. This is not a quality score: evaluation claims can be self-reported, may use incomparable datasets/settings, and must be reviewed in the model card/source (the result may be community-submitted). Hub search itself is ordered by downloads, so the candidate set is a bounded shortlist, not an exhaustive search.

Recommendations report the saved assumed context, declared context when available, estimated weights, KV cache, aggregate concurrency, effective RAM budget, largest single GPU free memory (when available), plus download-directory free space and a 5% artifact margin. Weight memory is estimated as artifact bytes × 1.25. If pinned model config exposes layer count, KV heads, and head dimension, the KV estimate uses FP16 and `2 × layers × KV heads × head dimension × 2 bytes × assumed context tokens`; otherwise the estimate is explicitly marked weights-only with unknown KV cache. The default assumed context is up to 4096 tokens (or a larger explicit requirement). Concurrency conservatively multiplies the full per-agent weight+KV estimate by saved maximum concurrency, as if every worker loads a separate copy. The single-agent candidate is filtered against the effective RAM budget; concurrent fit is reported separately. GPU comparison assumes full offload and compares with currently free memory on the largest one NVIDIA device; it does not combine GPUs or reserve memory. Estimates omit runtime-specific quantization overhead, allocator fragmentation, KV-cache format changes, and contention changes after sampling. They are planning estimates, not LM Studio's load estimate or measured performance. Treat the output as a shortlist, not a guarantee. Recommendation never starts a download; use `hf download` after reviewing the repository, license, evaluation evidence, and selected artifact. In the desktop Hugging Face view, “Recommend fit” provides the same shortlist, and download buttons remain disabled until model downloads are enabled and the disk check passes.

The automatic model selector chooses from installed LM Studio inventory and records a reason. It requires declared modality for image tasks and treats declared tool-use capability as a ranking hint rather than a hard filter because LM Studio metadata can be incomplete; observed local verified task outcomes take precedence over an unverified capability flag. Before each local inference turn, Xyst refreshes LM Studio's loaded-instance inventory. If the selected instance was idle-unloaded between tool turns, Xyst reuses another adequate instance or prepares the selected model again when automatic loading is enabled; it does not send a stale instance ID to inference. With automatic loading disabled, the run stops with a clear unavailable-instance error. It estimates the current session's text history and attached images against declared context limits, prefers models that fit the estimated RAM budget, and avoids unsupported publisher or name-based score bonuses. On a default local LM Studio server with NVIDIA telemetry available, automatic single-agent selection also samples up to three eligible models through `lms load --estimate-only` and prefers an estimate that fits current free VRAM; mission admission uses the same bounded estimates to coordinate parallel work when NVIDIA VRAM telemetry is available. Estimates can be unavailable or incomplete and do not guarantee a successful load or reserve memory from other processes. Context estimates use text length, a fixed allowance for image inputs, and reserved space for system instructions and tools; they are approximate and fall back to the best available model when no installed model declares enough context. Mission assignment estimates the bounded task prompt it will send, including GitHub trigger input and completed dependency results. The scheduler's model choice remains provisional until the agent has estimated the full persisted history and tool context; if that automatic assignment cannot fit, Xyst re-runs automatic selection and can enter the same bounded discovery/acquisition flow. Explicit manual model selections remain pinned. With local measurements enabled, any observed task outcomes are compared by verified completion rate; a model with measured zero completions is deprioritized against eligible models whose task reliability is still unmeasured. If all GPU-estimated candidates have zero verified task completions, the planner may make one bounded attempt with the best RAM-fitting, reliability-unmeasured candidate even when its GPU estimate is unavailable; the assignment records that VRAM fit is unknown. Models with at least three recorded inference calls each are otherwise compared by response success rate, output throughput, and median round-trip latency after capability, context, and resource filters. These local outcomes rely on Xyst completion evidence and are not independent quality evaluations. If no local LLM is installed, enabled discovery returns a recommendation when downloads are off; with downloads on, Xyst acquires and verifies an eligible model before continuing. Image tasks may automatically acquire only a candidate whose selected artifact set includes a matching projector and whose LM Studio inventory declares vision support. Explicit model selections do not trigger automatic acquisition.

`telemetry.localMetrics` is enabled by default and stores model key, input/output token counts when provided, inference duration, generation success or failure, and a session-level final task outcome in the local SQLite database. Task outcomes distinguish verified success, unverified completion, and failure. Xyst also records a coarse category (coding, research, document, spreadsheet, vision, workflow, or general) derived from the task request so selection can compare local outcomes for similar work; it does not store the prompt or upload telemetry. Older outcomes without a category remain available for general reliability fallback. Cancellations and non-final attempts within one uninterrupted run are excluded. If a session ends unverified and is later resumed with another model, the earlier model's terminal outcome is retained; the resumed model receives its own final outcome. Turn it off with `telemetry off`; turn it back on with `telemetry on`, and inspect the setting with `telemetry status`. Use `lm stats [model-key]` to inspect per-model inference sample count, response success rate, median latency, output tokens per second, and final task outcomes with their verified completion rate and task-category breakdown. The desktop exposes the same toggle and shows measurements on model cards. Automatic switching is a separate opt-in: after repeated inference failure, Xyst can switch once to another installed local LLM for the same session. A manually selected model is never replaced by local switching. A separate models.remoteFallback option can use a configured secondary LM Studio endpoint/model after local inference fails. It is off by default and asks for approval each run before sending the conversation, instructions, attachments, and tool results. Network and external-action policy are checked; unattended mission runs fail closed. Configure the endpoint and model in docs/configuration.md, and store any API token with xyst credential set lm-studio-remote-fallback api-token. Remote latency and success are not included in local model-selection telemetry.
