# Security model and current limitations

See the [extension threat model](EXTENSION_THREAT_MODEL.md) for extension assets, trust boundaries, attacker scenarios, residual risks, and the proposed signed capability-manifest contract.

## Threat model

This model covers a Xyst AI Assistant process launched by one interactive Windows or Linux user. Xyst AI Assistant uses that account's operating-system identity. It is not a service boundary between mutually untrusted users, and it cannot provide administrator/root access or protect the host from a hostile process already running with equivalent or greater OS privileges. The process isolation described below is defense in depth and is not production-certified until the platform escape and recovery reviews pass.

### Assets

| Asset | Security objective |
| --- | --- |
| User files, source code, and desktop session | Read or change only as allowed by the selected autonomy posture, OS account, and available sandbox. |
| Provider credentials and other secrets | Resolve only when needed; keep vault values out of model context and persisted sessions, and keep recognizable secret values out of session, audit, and ordinary diagnostic records. |
| User policy and configuration | Project content, model output, retrieved text, and extensions must not silently weaken user-selected autonomy, approval, or sandbox policy. |
| Sessions, goals, memory, indexes, approvals, and audit records | Preserve integrity and scope; treat user/model/tool-derived text as data rather than executable policy. |
| Processes and their descendants | Start only through the configured runtime policy; preserve cancellation and avoid signaling an unrelated process after identity changes. |
| Local control API and desktop bootstrap token | Allow the paired local UI to control the current process without exposing a reusable remote service credential. |

### Trust boundaries and untrusted inputs

1. **Model/provider boundary:** provider replies, tool-call arguments, model IDs, and error payloads are remote or local service input. A configured local endpoint is trusted to receive the prompts sent to it, but its output is still untrusted.
2. **Workspace/content boundary:** repository files, web results, screenshots, memory, goals, imported sessions, and tool observations may contain instructions intended to manipulate the model. They never change runtime policy.
3. **Tool/runtime boundary:** only the runtime validates schemas, evaluates the active policy, asks for approval where required, and decides whether execution is sandboxed. Model-supplied approval claims have no authority.
4. **Extension boundary:** MCP servers can execute code as the Xyst AI Assistant OS user unless a supported process sandbox constrains them. Skills are non-executable instructions. Signatures establish publisher identity and byte integrity, not that a package is safe.
5. **OS process boundary:** Bubblewrap on Linux and the packaged AppContainer helper on Windows provide requested isolation only when their backends are available and launch succeeds. Disabled sandbox mode and Unrestricted autonomy run under the current account's ordinary OS permissions.
6. **Local UI/API boundary:** the API binds to loopback and uses an ephemeral per-process bearer token. Same-user malware, debuggers, browser extensions with access to the page, or a compromised desktop process are outside the protection offered by loopback binding alone.

### Attacker capabilities considered

- A malicious or compromised model can request any tool described to it, emit malformed arguments, and follow prompt-injection text from workspace, web, screenshot, memory, or tool output.
- A malicious repository or document can change while a run is active, contain symlinks or hard links, and attempt traversal or race conditions against file and process setup.
- A configured MCP server or lifecycle hook can return malicious data, consume resources, or execute code with the Xyst AI Assistant account's privileges unless the applicable sandbox contains it.
- A remote provider can return malformed, oversized, delayed, rate-limited, or hostile responses. A configured local model server is not assumed to be safe merely because it is on loopback.
- Another process under the same OS account can race filesystem operations, inspect same-user state, alter mutable workspace contents, or interfere with non-isolated child processes.
- A privileged local attacker or a compromised kernel can read or alter process memory and files; protection against these attackers is not claimed.

### Threat scenarios and current residual risk

| Scenario | Runtime control | Residual risk / evidence still required |
| --- | --- | --- |
| Prompt injection asks the agent to disclose secrets or bypass approvals | Untrusted observations are labeled; approvals and tool policy are runtime decisions; AgentRuntime rechecks current approval rules after an approval wait and after pre-tool hooks, and reloads exact-action session grants at execution checks; Assisted mode redacts common credential forms, recursively scans nested JSON/tool arguments, and blocks common credential paths. | A policy change after the final check remains a race; detection remains pattern-based, and no text classifier can replace authorization. Expand secret canaries and source-provenance tests across all serialization/export paths. |
| Malicious tool arguments escape the workspace or overwrite a changed file | Schemas, path checks, symlink handling, approved diffs, and stale-base validation apply in Assisted mode. `read_file`, `edit_file`, and approval previews read through one opened handle, compare its identity with the re-resolved target, and reject final symlinks where supported. Writes and edits create an empty exclusive temporary file, revalidate the destination before writing proposed content, then revalidate again before atomic replacement; edits also verify the source hash. | Portable Node APIs do not provide race-free directory-handle traversal for every parent component, and a swap after the final validation still remains possible. Native reparse/link edge cases and replacement-race validation remain; unrestricted mode deliberately removes app-level workspace scope. |
| A workspace swaps a directory or file while semantic indexing scans it | The scanner canonicalizes directories, rechecks that paths remain inside the workspace, opens regular files with `O_NOFOLLOW` where available, compares opened handle identity and metadata, and bounds reads. A regression swaps an enumerated directory for an outside symlink and verifies no content reaches the embed callback. | Portable Node APIs do not provide race-free `openat` traversal for every parent component; platform-specific race and reparse-point validation remains. |
| A shell or MCP child reads host files or reaches the network | Workspace-isolated process modes fail closed when their backend is unavailable; Linux Bubblewrap validates workspace mounts and checks the mounted root device/inode before the requested command starts, while Windows uses AppContainer and Job Object controls. The Ubuntu 24.04 WSL Bubblewrap integration passes host-file/environment/temp isolation, network denial, read-only behavior, hard-link/symlink handling, nested-user-namespace denial, background execution, and stale workspace-root rejection. Windows AppContainer integration verifies denial of twelve sensitive process-object rights against the host test process and an unrelated same-user sibling, in addition to workspace, network, timeout, and cancellation boundaries; native preflight tests reject a real directory junction as a reparse point. | Intra-workspace mutation races and broader Linux escape tests remain open. The required Windows audit symlink fixtures currently fail to create their links with `EPERM` in this environment; they passed in a prior administrator-approved run, but this run does not count them as verified. Hosted execution remains required. Alternate reparse tags, later ACL-crash transitions, descendant, and broader object-access matrices remain incomplete; tests cover forced host death during an active grant and retry after ACL restoration. None mode is not containment. |
| A secret enters a prompt, transcript, trace, or error | Vault references resolve at request time and are sent only in the intended provider/tool request. Session writes redact structured and recognizable string secrets into a separate persisted clone in every autonomy mode; audit and opt-in telemetry records are content-minimized. | Detection is pattern-based, legacy files are not bulk-rewritten, and active Unrestricted model context/tool results remain raw by design. Redaction cannot guarantee removal of arbitrary unmarked secrets, binary/base64 data, or values in unsupported encodings. Review telemetry destinations before enabling export. |
| Prompt injection or an unsafe MCP package executes code | Signed package verification, explicit activation, revocation checks, and runtime policy protect package lifecycle; instruction skills do not execute code. Legacy Streamable HTTP session IDs stay in memory and are only sent to their configured endpoint; the current protocol remains stateless. | Signatures do not prove code safety or constrain direct OS APIs. Executable MCP packages require independent review and sandbox enforcement; Streamable HTTP remains unavailable in workspace-isolated mode. |
| A web page or local UI origin forges an authenticated control request | Loopback binding, bearer authorization, Host/origin checks, and strict browser content policy constrain the API. | Same-user process compromise and the authenticated desktop/browser process remain trusted; complete cross-browser/platform pairing review is open. |
| A killed manager leaves processes, grants, locks, or partial state | Atomic session writes, identity-checked recovery, lease ownership, and explicit stale-state recovery preserve or diagnose some state. Interrupted subagent tasks are marked failed only after their owner is proven absent; the parent can then retry in a fresh worktree while preserving the recovered attempt. Linux pidfd recovery has a force-killed-manager integration; Windows Job Object recovery covers direct and nested descendants, including a second wave created while recovery attaches the tree. A Windows WMI integration confirms an out-of-tree process is left alive by managed-tree recovery and can only be stopped through its own captured identity. | WMI/COM-created processes outside the managed OS-parent tree are deliberately not attributed to a Xyst background task; users invoking those launch paths must manage their lifetime themselves. Physical Ubuntu Desktop recovery, later journal commit and ACL/profile crash boundaries, and broader orphan cleanup remain incomplete; recovery tests cover forced host death during an active grant, retry after ACL restoration, cleanup of interrupted temporary journals, preservation of a pre-existing temp-name collision, cleanup after journal commit failure without replacing an existing destination, and retry after profile deletion before journal removal. Ambiguous identity fails closed. |
| The user selects Unrestricted mode and the model performs a destructive action | The mode is explicitly user-selected in user configuration/settings and is not switchable by project or model text. Session persistence still applies best-effort secret redaction without mutating the active run. Hard file, directory-listing, screenshot, and JSON tool-result ceilings limit individual operations. | Unrestricted mode intentionally bypasses Xyst AI Assistant approvals, configured denials, workspace scope, transient model-context/tool-output redaction, and configured budgets. Runtime byte/entry ceilings are availability limits, not authorization or containment boundaries. Its effective execution boundary is the OS account and user judgment; its active model/provider can receive raw content read during the task. |

### Autonomy and sandbox semantics

**Assisted** applies Xyst AI Assistant's configured path scope, approval rules, deny rules, secret filters, and budgets. These application controls do not contain a process that runs without an OS sandbox. **Unrestricted** removes Xyst AI Assistant's app-level approval and workspace restrictions so automation can use the launching account's accessible files, desktop, processes, and environment; it does not elevate that account or bypass OS permissions. Hard runtime ceilings still cap file operations, directory listing work, screenshots, and JSON tool results. Active model context and tool results remain raw in this mode, while every session save redacts recognizable credential patterns in a persisted clone; the in-memory run keeps its original content. This pattern-based persistence filter is not a guarantee against arbitrary secret formats. **Workspace sandbox modes** request a platform OS boundary and fail closed when the backend cannot be used. `workspace-write` allows changes in the selected workspace, while `workspace-read` mounts it read-only. `read-only` exposes local inspection tools and hides process-capable tools. The presence of an installed helper is capability evidence only; it does not prove a particular action ran isolated. Desktop automation is disabled when the required process sandbox would prevent access to the host session.

The supported isolation mechanisms and their current test status are documented in [Platform support](PLATFORM_SUPPORT.md) and [ADR 0010](adr/0010-windows-process-isolation.md). Do not make production containment claims until native Windows and Linux escape/recovery testing and independent security review are complete.

## Implemented protections

- In the `assisted` profile, file tools resolve inside the selected workspace and validate existing symlink targets.
- Tool arguments are checked against schemas and required fields before execution.
- In the `assisted` profile, writes, edits, and shell calls require policy approval by default.
- Session approvals can grant only an exact tool-and-arguments match, with a bounded expiry; grants can be revoked and are discarded when a session is forked.
- Fresh installs and the example configuration select unrestricted autonomy; users can choose `assisted` explicitly, which keeps shell access opt-in.
- Executable calls use argv directly; shell interpretation is explicit through `run_shell_script`. That tool is exposed only when process execution is enabled, requires normal approval in assisted mode, follows the configured sandbox/environment/workspace policy, and uses PowerShell on Windows or Bash on Linux. Unrestricted mode does not ask for Xyst AI Assistant approval.
- `computer_control` exposes the current interactive desktop's accessibility tree and can click, drag, and vertically/horizontally scroll at screen coordinates; click accessible controls; enter text; capture screenshots for vision-capable models; and send validated CTRL/ALT/SHIFT/WIN (SUPER) combinations with letters, digits, navigation keys, F1-F24, Print Screen, Pause, Menu, and numeric keypad keys. Assisted mode requires approval; unrestricted mode does not. Desktop content is untrusted model input and may contain private information. The accessibility view does not expose controls that lack accessibility metadata. Required process-sandbox mode disables desktop control because the action must reach the host session. Windows uses the system UI Automation API through Windows PowerShell 5.1 plus fixed Win32 pointer and keyboard input; Linux requires a graphical session and pyatspi, with xdotool for X11 input or wtype/ydotool for Wayland input. Coordinates and keys are validated and passed as structured data/argv. Wayland pointer automation depends on ydotoold and the account's access to `/dev/uinput`.
- Provider credentials are referenced by environment-variable name and are not copied into prompts or session records.
- In the `assisted` profile, common credential files (`.env`, private-key paths, cloud credential directories, and token config files) are blocked from file reads; credential-like assignments and common token forms are redacted in tool output.
- In the `assisted` profile, values matching the current credential detector in user prompts are rejected before provider calls. Matching tool-call arguments are omitted from persisted transcripts and denied.
- User-maintained project memory and goal writes redact credential-like values; the runtime redacts them again when building model context so older stored records do not bypass the filter.
- In the `assisted` profile, child processes inherit a filtered environment that omits common credential names and handles (including SSH-agent and askpass variables), credential-provider config pointers, Git's environment-driven config overrides, and runtime code-injection variables such as `NODE_OPTIONS`, `PYTHONPATH`, and dynamic-library preload hooks. Unrestricted autonomy inherits the full user environment. Explicit MCP credential references remain scoped to their configured server process.
- Direct process launch uses argv. With `sandbox.mode = "none"`, it runs with the current user's filesystem/network privileges; approval is not containment.
- Workspace-isolated Linux process execution uses Bubblewrap with a limited system mount set, a writable or read-only workspace mount according to mode, private temporary storage, a cleared environment, isolated network/PID/IPC/user namespaces, and disabled nested user namespaces. Launch requests that nested-user-namespace isolation and asserts that Bubblewrap actually disabled it, so unsupported kernel or runtime behavior fails before the command starts. Before launching, it reads Linux mount metadata and rejects nested mount points (including same-filesystem bind mounts), walks the workspace without following symlinks, rejects special files, and rejects regular-file hard links whose other names are outside that workspace; links wholly contained within the workspace are allowed. This path-based preflight does not prevent a separate host process from changing the tree after the scan and before process start. Workspace-isolated Windows process execution uses the packaged AppContainer helper with a workspace ACL that is read-only in `workspace-read` mode, private temp, no network capabilities, bounded stdio capture, and a kill-on-close Job Object. Helper discovery resolves the active workspace and rejects a helper executable contained within it, so a sandboxed process with workspace write access cannot replace the host-launched helper; CLI and API capability status use the same workspace-specific check. The helper suppresses inheritance on its protocol handles while creating the child because Windows rejects a handle-list attribute combined with AppContainer security capabilities. Both paths fail closed if their backend is unavailable. Windows AppContainer escape, recovery, and supported-edition validation are incomplete; do not treat this prototype as a production security boundary. See [ADR 0010](adr/0010-windows-process-isolation.md).
- Tool results are persisted and sent back to the model as `untrusted_observation` envelopes with tool and call-ID provenance. The envelope is a machine-readable reminder; policy remains enforced by the runtime and operating-system boundary.
- Tool-result injection heuristics are strictly report-only. The detector examines at most 65,536 characters from at most 4,096 nested values and stops at depth 12. It emits only a fixed detector version, the tool name, and allowlisted signal codes (`instruction_override`, `role_impersonation`, `credential_exfiltration`, `approval_bypass`); it does not copy snippets or matched text into the signal. The ordinary tool observation remains in the transcript as before, and the signal does not alter the model request, approve/deny tools, or change sandbox policy. The UI warns that a pattern can be a false positive. No signal is not evidence that content is safe: the detector can miss paraphrases or instructions after its scan bounds. False-positive and recall rates have not yet been measured on a representative corpus, so this must never be used as an authorization or enforcement decision.
- Tool output and process output are size limited.
- Background process starts use the active profile's approval, environment, and workspace policies; records are session-bound for model access. Process state-directory components reject symbolic links, stored records are opened without following links and are bounded to 8 MiB, and writes recheck the state-directory identity before replacement. Portable filesystem APIs cannot eliminate every same-user path-swap race. Authenticated API stop/removal requests are audited.
- A live process started by another manager instance is reported as unmanaged. After its owner exits, recovery requires a matching OS identity: Linux checks boot ID, process start ticks, and argv hash; Windows checks process creation time and image path hash. A reused PID is marked `identity_mismatch`, and unavailable identity remains `orphaned`; neither can be signaled or deleted. Linux holds a pidfd for the leader while checking identity and signaling its process group, preventing PID/PGID reuse during the signal operation; Python 3.9+ and Linux 5.3+ pidfd support are required, otherwise stop fails closed. If the group leader has already been reaped, remaining descendants cannot currently be identified and safely stopped. Windows revalidates the root, captures verified OS-parented descendants, pins their handles, assigns them to a kill-on-close Job Object, and terminates only that verified tree. Processes created out-of-tree through WMI/COM are outside this managed recovery boundary; Xyst leaves them untouched rather than guessing ownership. A Windows integration test exercises that boundary. Windows identity inspection uses PowerShell, and all identity failures fail closed.
- Session writes use a temporary file and rename to avoid partial JSON records. Before writing, the store sanitizes a clone of the validated session using structured-field and recognizable-string credential patterns; it leaves the active in-memory session untouched so the current run retains its intended context. This applies in Assisted and Unrestricted modes, but is not a promise to find arbitrary or unmarked secrets. Existing legacy records are not rewritten until a later save.
- Session exports may include a redacted snapshot of their referenced project goals; import adds missing goals, skips identical IDs, and rejects conflicting goal IDs without leaving an imported session behind. Project backups are portable JSON bundles that may contain conversation transcripts, memory, and goals. Export checks stored records for corruption, strips session grants and worktree paths, and writes the file with owner-only permissions where supported. Restore validates and stages the complete bundle before one directory rename and refuses any destination with existing `.agent` state. Backups can contain sensitive user or repository content; protect and encrypt them with the operating system's storage controls. Machine configuration, credentials, approval policy, audit and usage ledgers, processes, worktrees, and semantic indexes are not included. Session IDs are regenerated on restore; goal IDs are preserved.
- CLI worktree creation places checkouts under `.agent/worktrees` and disables Git hooks, fsmonitor, and configured smudge/process filters for that operation. Git still runs with the current account's permissions; do not treat worktree creation as a sandbox for untrusted repositories.
- Worktree leases persist a random token and OS process identity without raw command lines. Inspection is read-only; explicit stale-lock recovery requires a same-host process-identity result of absent or PID-reused and rechecks the lock's file identity and token before deletion. Remote, legacy, malformed, and unverifiable leases fail closed. Dirty worktrees are never deleted by lock recovery.
- Subagent task owners and concurrency slots persist bounded OS process identity records without command lines. Interrupted-task inspection is read-only; explicit recovery requires verified owner exit, removes only the matching stale slot/worktree lease, and marks the task failed while preserving its worktree. Legacy or unverifiable owner/slot records fail closed.
- Local control API binds to IPv4 loopback, uses an ephemeral per-process 256-bit bearer token, validates Host and peer addresses, accepts same-origin UI requests, and permits cross-origin browser requests only for explicitly configured origins. Tokens are returned once on the server process stdout for a trusted parent to capture.
- Authenticated `GET /v1/models` contacts only configured provider profiles, limits concurrency and request duration, rejects HTTP redirects, and returns bounded model IDs plus safe error codes. Credentials resolve only for that provider request; provider response details are not copied into the API response.
- The `tools.autonomy = "unrestricted"` profile intentionally disables application-level file, command, sensitive-path, transient model-context/tool-output redaction, approval (including for enabled web search), deny-rule, configured token/cost budget, directory-entry, and tool/process output-size restrictions. It permits absolute paths across the machine, recursive/search traversal, shell-capable process invocation, and the full current-user environment. Session saves still redact recognizable credential patterns on a persisted clone; active task context is not changed, and arbitrary secret formats may escape the pattern filter. It is user-config-only; a project `.xyst.toml` cannot enable it. The operating system's account privileges remain the ultimate boundary, and the profile cannot elevate them. Provider context/output limits, host resources, and explicit cancellation still apply.
- The bundled browser UI is served from the loopback origin with a strict content security policy, no cross-site loading, and no persistent token storage. Its same-origin page receives the process token in a meta element; user and workspace content is rendered with text nodes rather than HTML parsing.
- MCP stdio, Streamable HTTP, and legacy HTTP+SSE servers connect only when explicitly enabled in user configuration. Project config cannot install, launch, or declare them. Advertised tools are schema-checked, namespaced, bounded, and routed through AgentRuntime; in assisted mode they require approval. Server descriptions, schemas, and results are untrusted input. Credentials resolve only through named environment variables or the OS vault. HTTP requires HTTPS outside loopback, rejects redirects, and never logs headers or endpoint URLs; the endpoint advertised over SSE must share the configured origin. Required mode supports Linux stdio processes under Bubblewrap with no network and a read-only signed package mount; MCP environment references and both HTTP transports remain unavailable. Persistent MCP sandboxing remains unavailable on Windows.
- Instruction skills load only from absolute user-configured directories. The initial `SKILL.md` parser accepts exactly a name and description header, bounds candidate count and bytes while reading from one verified regular-file handle, rejects symlinks, malformed UTF-8, and duplicate names, and exposes content as untrusted reference data through the normal observation envelope. Project config cannot add skill roots. Skills do not execute code.
- Lifecycle hooks are opt-in and executable only from user configuration; project configuration cannot install them. They use direct argv process launch, bounded stdin/output and timeout, and the configured process sandbox when required. Pre-hook failures stop the related model/tool action; advisory hook failures emit metadata-only events. Hook scripts execute with the user's process privileges and may inspect the workspace, so they must be trusted.
- Extension packages are verified against user-configured Ed25519 public keys before staged installation. The signature covers package identity, version, type, every file digest, optional MCP launch entry point, and optional versioned capability declarations; legacy version-1 manifests without declarations remain valid. The bounded capability schema rejects unknown names, duplicates, malformed/wildcard scopes, and executable capability requests from instruction-only skills. Declarations are publisher claims, not grants. Runtime checks MCP feature categories against declarations but does not enforce process-level filesystem, network, desktop, or environment restrictions. Undeclared files, symlinks, path traversal, portable path collisions, revoked keys, and revoked package revisions are rejected. Authenticated update downloads use a bounded in-memory JSON bundle; the signed feed manifest digest and full package signature/file digests are checked before writing verified bytes to the version-addressed store. Package-update and revocation feed cache commits are cross-process serialized and revalidate the latest sequence before writing, preventing a late older response from rolling back a newer signed cache. A crashed writer's lock fails closed pending operator verification. Downloads never auto-activate or execute package code. Signed skills require explicit activation, are reverified at runtime, and remain untrusted instructions. Optional revocation feeds use signed, sequence-checked data with expiry; runtime reads never fetch remotely and fail closed for active installed packages when configured revocation data is unavailable or expired. Signed MCP packages remain inert until both explicit extension activation and a matching enabled user MCP server entry are configured.

## Known limitations

- With `sandbox.mode = "none"` (the default), the process adapter runs with the user's operating-system privileges. Approval is a user confirmation step, not containment. Enabling it for an untrusted repository is unsafe. Linux Bubblewrap and Windows AppContainer modes still require broader escape testing on supported systems before they can be treated as production boundaries.
- Environment variables remain available for development. `api_key_secret` resolves credentials from Windows Credential Manager or Linux Secret Service at provider execution time. There is no plaintext fallback; unavailable vault helpers/services fail closed. Secret values are provided to helpers through stdin and are not included in argv or helper diagnostics. Linux key listing queries only Secret Service item attributes over D-Bus; it never calls `GetSecret` or reads credential payloads.
- Credential detection uses known paths and token/assignment patterns. It cannot identify every custom credential format or arbitrary encoded value; it is a protective filter, not a data loss prevention guarantee.
- Credential-like values in legacy session, memory, or goal records are redacted when those records are resumed, compacted, or added to model context; no bulk migration rewrites untouched historical files.
- Process network isolation is implemented for Linux Bubblewrap and Windows AppContainer one-shot calls, but requires broader escape testing. There is no general outbound network policy, seccomp/Landlock policy, extension sandbox, or independent security review yet.
- TOML support is an intentionally documented subset; unsupported syntax fails with a line-specific error.
- Local model endpoints are treated as trusted configured services. Do not point them at an untrusted network endpoint with credentials.
- Logs currently avoid serializing request headers and environment contents. Production tracing/export requires a separate redaction review.
- The 2026-10-26 RustSec audit found no vulnerability-severity advisories after Tokio was updated to 1.54.1. The affected GLib 0.18.5 iterator code is patched in `gui/desktop/src-tauri/vendor/glib-0.18.6-xyst` using the upstream mainline fix; its optimized `test_variant_iter_array` regression passes twice, and Ubuntu WSL `cargo check --locked` verifies the Linux app integration. The locked Linux dependency resolves to this local source. CI denies unsound advisories with a `RUSTSEC-2024-0429` exception for this patch; four unmaintained-crate warnings remain. See the vendor `PATCHES.md` for provenance and removal criteria. Hosted CI and independent security review remain open.

## Security release gates

Do not represent the product as securely sandboxed until escape tests pass on supported Windows and Linux environments and an independent review has assessed the boundary. Extension execution, arbitrary shell, network access, and secret-vault integration each need their own threat-model coverage before production release.
