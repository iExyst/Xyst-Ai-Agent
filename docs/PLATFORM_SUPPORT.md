# Platform support and data locations

## Initial support target

The first release target is **Windows 11 x64 (25H2 or newer)** and **Ubuntu Desktop 24.04 LTS x86-64**. Windows uses the NSIS installer; Ubuntu uses a DEB package. A Linux AppImage is available as a portable package; its extraction, packaged service, accessibility, resize, and restart smoke passed under Ubuntu 24.04 WSL/Xvfb, and hosted CI is configured but has not yet been observed. DEB remains the supported install and update path. RPM packages are not produced until the Tauri RPM bundler can complete and pass package lifecycle tests. Other Windows editions, Linux distributions, and CPU architectures are outside this initial support commitment. ARM64 runtime archives exist, but ARM64 remains experimental until native CI and packaged runtime tests cover both operating systems. macOS is outside the product scope.

The CI matrix selects Windows Server 2022 and Ubuntu 24.04 runner labels with Node.js 22 and 24; hosted image patch revisions still advance. The Windows runner validates build and service behavior but does not substitute for a Windows 11 client release smoke. The desktop workflow is configured to build native Windows NSIS and Linux DEB/AppImage packages, run a Windows install/runtime/uninstall smoke, Linux DEB install/upgrade/rollback/runtime smoke, and AppImage extraction/source/service/desktop smoke, and upload each artifact. Native release validation on the named end-user targets remains required before calling them verified support.

The CLI requires Node.js 22 or newer; the current release test matrix validates Node.js 22.x and 24.x. The desktop bundles Node.js 24.22.0 from the pinned runtime manifest. Revisit the minimum Windows servicing release and tested Node.js majors before each release. Microsoft currently lists Windows 11 25H2 Home/Pro servicing through 2027-10-12; Canonical lists Ubuntu 24.04 LTS standard security maintenance through May 2029 ([Microsoft lifecycle](https://learn.microsoft.com/en-us/lifecycle/products/windows-11-home-and-pro), [Ubuntu release cycle](https://ubuntu.com/about/release-cycle)).

The desktop shell depends on the platform WebView; Linux builds additionally require the packages listed in the desktop build instructions. Linux process isolation requires a trusted system Bubblewrap executable and compatible user, mount, PID, network, and IPC namespaces; required isolation fails closed if Bubblewrap cannot establish the configured boundaries. Linux recovered process stopping requires pidfd support (Linux 5.3 or newer); without it, recovered stop operations fail closed. Linux desktop automation requires an interactive graphical session and AT-SPI. X11 input uses xdotool; Wayland key/text input uses wtype, and Wayland pointer input uses ydotool with its user-session daemon and `/dev/uinput` access. Screenshot capture requires grim on Wayland or ImageMagick on X11. These optional capabilities are detected or fail with an explicit error.

Workspace-isolated Windows process execution uses the packaged AppContainer helper, exposing the selected workspace and private temp, starting without network capabilities, and cleaning up its Job Object on timeout or cancellation. Helper discovery is scoped to the canonical active workspace and rejects a helper stored within that workspace; CLI and API capability reporting use the same check. A live Windows helper integration run passed workspace-boundary, loopback-denial, shell/non-shell, and failure-closed checks; Rust formatting, strict Clippy, native unit tests, Tauri compilation, and helper packaging also passed on the Windows host. Broader escape/recovery validation and independent review remain open. Workspace isolation also disables unrestricted autonomy and desktop automation. Do not describe disabled isolation as a sandbox.

The initial end-user target is now named. Local validation on Ubuntu 24.04 under WSL 2 passes the required Bubblewrap/pidfd/link tests, Linux browser smoke, Tauri host checks, and Debian package build, installation, service startup, purge, and configuration-retention checks. The Linux Secret Service adapter also passes real set/get/list/delete checks against a temporary unlocked GNOME Keyring in WSL; key listing reads D-Bus item attributes without requesting secret values. Ubuntu CI now installs the keyring tools and requires the same integration check with `pnpm check:linux`, though a hosted run has not yet been observed. These checks do not verify a native Ubuntu Desktop installation, graphical session, or login-session keyring startup. The release support gate remains open until Windows 11 client and Ubuntu Desktop behavior are confirmed, ARM64 is covered or kept experimental, native Linux Secret Service session behavior is validated, and independent security review is complete. CI runner labels and WSL validation alone do not prove end-user support.

## Persistent data map

| Data | Location | Scope and handling |
| --- | --- | --- |
| User TOML configuration | Windows: `%APPDATA%\Xyst AI Assistant\config.toml`; Linux: `$XDG_CONFIG_HOME/xyst-ai-assistant/config.toml`, defaulting to `~/.config/xyst-ai-assistant/config.toml` | User-level provider, tool, and runtime settings. |
| User data root | Windows: `%LOCALAPPDATA%\Xyst AI Assistant`; Linux: `$XDG_DATA_HOME/xyst`, defaulting to `~/.local/share/xyst` | User-level data. Global memory is stored at `.agent/global-memory.json` here only when enabled in user config. |
| Runtime settings sidecar | `<config.toml>.runtime.json` | Authenticated settings API overrides; atomically written with user-only permissions where supported. |
| Provider credentials | Windows Credential Manager; Linux Secret Service | User vault. Credential values are resolved only for provider/tool requests. Linux requires a working Secret Service and `secret-tool`; Linux key-name listing also requires `gdbus` from `libglib2.0-bin`. The DEB declares both command-line packages as dependencies. |
| Project sessions and compaction archives | `<workspace>/.agent/sessions` and `<workspace>/.agent/compactions` | Workspace-specific JSON records and archives. Include or exclude them from version control intentionally; they may contain task text and tool observations. |
| Project memory and goals | `<workspace>/.agent/memory` and `<workspace>/.agent/goals` | Workspace-specific editable records. Treat them as user data. |
| Audit, approvals, usage, process, subagent, and optional observability records | `<workspace>/.agent/` subdirectories | Workspace-scoped operational records. Optional observability is disabled by default and keeps an active JSONL file plus one rotated backup; review before sharing. |
| Semantic index | `<workspace>/.agent/retrieval` | Vectors and source metadata, not indexed source text. |
| Managed worktrees | `<workspace>/.agent/worktrees` | Git worktree checkouts; dirty worktrees are retained until explicitly handled. |
| Desktop window geometry | OS application config directory | Small validated bounds record; restored only if it intersects a connected display. |
| Windows sandbox recovery journal and lock | `%LOCALAPPDATA%\Xyst AI Assistant\SandboxRecovery` | Per-user recovery metadata for temporary workspace ACL grants; invalid or unrecoverable entries stop required-sandbox launches and remain for diagnosis. |

Project records remain under the workspace's `.agent` directory; user-level global memory is separately stored under the platform user data root and is disabled by default. Global memory is not migrated from project memory. Back up or export project data before deleting a workspace; review global memory before backing up or sharing the user data directory.

## Network and telemetry

The desktop service enables the bundled Node.js runtime's environment-proxy support when `HTTP_PROXY` or `HTTPS_PROXY` (or the lowercase variant) is present. On Windows it also reads the current user's enabled manual Internet Settings proxy when the corresponding environment variable is absent; per-protocol HTTP/HTTPS servers and bypass entries are supported. Environment variables take precedence. It preserves existing `NO_PROXY` rules and adds `localhost`, `127.0.0.1`, and IPv6 loopback so LM Studio and the local control API stay direct. Set `NODE_USE_ENV_PROXY=0` before launching the desktop app to opt out. The CLI can use the same standard variables by starting Node with `NODE_USE_ENV_PROXY=1`; this requires Node.js 22.21 or newer for `fetch()` proxy support. PAC/WPAD scripts, Windows `<local>` bypass semantics, automatic Linux desktop proxy discovery, and proxy authentication UI remain open.

Local structured lifecycle recording is opt-in through `[observability].enabled`; it excludes prompt text, file paths, tool arguments/results, and raw provider errors. Setting `console_enabled = true` additionally writes those same allowlisted JSON Lines records to the service's standard error stream. A separate opt-in OTLP/HTTP JSON trace exporter requires user TOML, the master observability switch, and an explicit HTTPS or loopback endpoint; it sends only bounded allowlisted lifecycle metadata, rejects redirects, and resolves auth headers from environment or OS-vault references. Provider requests, web search, remote embeddings, configured telemetry collectors, local API calls, and MCP servers are the network-capable integrations. Local model discovery is loopback-only. Remote embedding use requires explicit configuration; keyless Automatic search (recent GDELT news and Wikipedia references) is enabled by default and each query remains approval-gated in Assisted mode. The local control API binds loopback and requires a per-process bearer token.

## Release gate

Before claiming production support, pin and test specific Windows editions and Linux distributions, exercise x86-64 and ARM64 desktop builds, verify clean install/upgrade/uninstall behavior, test Linux Secret Service and GUI integrations, and complete platform-specific sandbox and security reviews. Until then, describe this repository as an actively developed foundation.
